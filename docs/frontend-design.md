# Frontend-design «Перекуп-помощник» — чертёж (v1, draft)

> **Цель.** Лицо продукта поверх готового API: Telegram mini-app (телефон-first), тот же код — веб-кабинет,
> полноценный бот через кнопки/визарды, Sheets-мост. Сначала ЭТОТ чертёж (утверждаем форму) → потом
> реализация экран за экраном, без переделок.
>
> **Что НЕ трогаем.** «Завод» (ингест→категория→ключ→condition→медиана→скоринг) и «Бэкенд» (пилоны 1a–2b:
> идентичность, RLS, auth план Б, RPC-поверхность) — живые и проверены на проде (экзамен 23×0, изоляция,
> журнал-математика). Фронт только ВЫЗЫВАЕТ существующие RPC. Все §4-решения и аудит-каноны в силе.

---

## Решения владельца по фронту (зафиксированы 20.06)
1. **Телефон-first.** Главное — Telegram mini-app на телефоне. Веб-кабинет — ТОТ ЖЕ код, открытый в браузере
   (через Telegram Login), но вторичен — после mini-app.
2. **Главный экран = дайджест/сводка.** При входе — короткая сводка: свежие сочные находки + прибыль за период
   одним взглядом. Не вываливаем всё; вглубь — по тапу.
3. **Авто-тема под Telegram.** Mini-app наследует тему клиента (светлая/тёмная — как у юзера). Максимальная
   «родность» в TG: цвета из `themeParams`, нативные кнопки.

---

## 0. Принципы фронта
1. **Тонкий клиент.** Вся логика (фильтр, скоринг, навар, доступ) — на сервере (RPC). Фронт рисует и зовёт.
   Никаких копий правил на клиенте (дисциплина NEW-4 распространяется и на фронт).
2. **Тихо лучше, чем ложно.** Цена/навар «в тесте» до рубильника — не показываем выдуманную выгоду. Ошибка
   RPC → явное сообщение пользователю (`error.msg`), не молчание и не мусор.
3. **Один канон вызова.** mini-app, веб-кабинет и бот зовут ОДНИ и те же RPC. Бот — не отдельная логика,
   а второй вид того же API.
4. **Секреты — на сервере.** В клиенте только **публичный anon-key** Supabase (он безопасен: данные стерегут
   `verify_initData` + RLS). Bot-token/service-key/ProxyAPI — никогда не в mini-app и не в git.

## 1. Архитектура одним экраном

```
            TELEGRAM (телефон)                          БРАУЗЕР (вторично)
        ┌────────────────────────┐                 ┌────────────────────────┐
        │  mini-app (web-app)     │                 │  тот же web-app         │
        │  Telegram WebApp SDK    │                 │  Telegram Login Widget  │
        │  initData (подпись)     │                 │  login-данные (подпись) │
        └───────────┬────────────┘                 └───────────┬────────────┘
                    │  POST /rest/v1/rpc/<fn>                   │
                    │  apikey: ANON (публичный)                 │
                    │  body: { p_init_data, ... }               │
                    ▼                                           ▼
        ┌──────────────────────────── SUPABASE (PostgREST) ──────────────────────────┐
        │  RPC: me / journal_* / finds_* / config_*   (security definer)              │
        │   └─ verify_initData(init_data) → client_id → работает ТОЛЬКО по нему        │
        │   RLS — второй пояс. Конверт ответа: { ok:true, data } | { ok:false, error } │
        └────────────────────────────────────────────────────────────────────────────┘

   БОТ (n8n, параллельно):  Telegram getUpdates → tg_router/tg_poll → те же RPC → ответ кнопками
   ПУШ (n8n, тень):         push_queue → карточка со светофором → Telegram (после рубильника/chat_id)
```

**Идея:** «две двери — одни данные». Никакого своего бэкенда у фронта нет. mini-app/кабинет/бот — три входа в
одну API-поверхность под одной системой прав. Аутентификация — **подписью Telegram на каждом вызове** (план Б),
JWT-сессии нет → клиент не хранит токен, просто прикладывает `initData` к каждому запросу.

---

## 2. Стек — простой, без тяжёлых фреймворков

Приложение = формы + списки + вызовы RPC. React/сборка не нужны. Берём:
- **Vanilla HTML/CSS/JS** (один `index.html` + модульные `.js`), либо лёгкий слой (Alpine/Preact) если станет тесно.
- **Telegram WebApp SDK** (`telegram-web-app.js`) — даёт `initData` (аутентификация), `themeParams`/`colorScheme`
  (авто-тема), `MainButton`/`BackButton`, `HapticFeedback`, `showConfirm`, управление вьюпортом.
- **Вызов API — прямой `fetch` к PostgREST** (или `@supabase/supabase-js`, но fetch достаточно):

```js
async function rpc(fn, params = {}) {
  const r = await fetch(`${SUPABASE_URL}/rest/v1/rpc/${fn}`, {
    method: 'POST',
    headers: { apikey: ANON_KEY, Authorization: `Bearer ${ANON_KEY}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ p_init_data: Telegram.WebApp.initData, ...params })
  });
  const env = await r.json();            // единый конверт {ok,data} | {ok:false,error}
  if (!env.ok) throw new Error(env.error?.msg || 'RPC error');
  return env.data;
}
```

**Почему так:** хостинг — просто статика (любой HTTPS); ноль build-pipeline; совпадает с духом проекта
(`site/index.html` — тоже vanilla). Апгрейд на фреймворк — только если экраны разрастутся.

## 3. Аутентификация и онбординг

### 3.1 mini-app (телефон) — `initData`
Telegram отдаёт `Telegram.WebApp.initData` (подписанная строка). Прикладываем её к КАЖДОМУ RPC как `p_init_data`.
Сервер (`verify_initData`, пилон 1c) проверяет HMAC bot-token'ом из Vault → `client_id`. Токен на клиенте не хранится.

### 3.2 Онбординг — по инвайт-коду (решение владельца §12 бэкенда)
Сейчас `verify_initData` для незнакомого Telegram-id кидает `NOT_INVITED`. Нужен путь редемпции:
- Первый вход без личности → экран «введи код приглашения».
- Новый RPC **`redeem_invite(p_init_data, p_code)`** (фронт-этап, ~небольшой): проверяет подпись, ищет `invite_codes`,
  создаёт/привязывает `client_identities` (telegram user_id → client_id), гасит код (`used_by/used_at`).
- Таблица `invite_codes` уже есть (пилон 1a); редемпция — единственная недостающая серверная деталь онбординга.

### 3.3 Веб-кабинет (вторично) — Telegram Login Widget
Тот же web-app в браузере. Вход — Login Widget (та же телеграм-личность → один `client_id`). ВНИМАНИЕ: формат
подписи Login Widget ОТЛИЧАЕТСЯ от WebApp (`secret = SHA256(bot_token)` против `HMAC(bot_token,"WebAppData")`).
→ нужен брат-валидатор **`verify_login_widget`** (маленький, по аналогии). Делаем на этапе кабинета, не сейчас
(телефон-first). До тех пор кабинет открывается ВНУТРИ Telegram (Desktop) и работает на `initData`.

### 3.4 Идентичность Вовчика — проверить
`client_identities.external_id` должен быть **числовой telegram user_id** (для лички chat_id == user_id). Если в
`client_configs.chat_id` лежит не его user_id — вход не сматчится. Сверить при подключении (задача владельцу §12).

## 4. Экраны (дайджест-first)

Шаблон: **ЦКП · RPC · показывает · действия.** `*` = зависит от реальных цен (до рубильника скрыто/«в тесте»).

### 4.1 Главная · Дайджест (стартовый экран)
- **ЦКП:** за 3 секунды — «есть ли что брать» и «как идут деньги».
- **RPC:** `finds_list({limit:5})` (топ по баллу) + `journal_dashboard()`.
- **Показывает:** блок «🔥 Свежие находки» (3–5 мини-карточек) + блок «💰 Сводка» (навар за месяц, в наличии,
  сделок, средняя маржа). Кнопки-переходы: «Все находки», «Журнал».
- **Действия:** тап по находке → карточка (4.3); тап по сводке → дашборд (4.6).

### 4.2 Находки · Лента
- **ЦКП:** весь персональный поток сочного, отсортирован по баллу.
- **RPC:** `finds_list({category?, min_score?, limit, offset})` (фильтр+скоринг клиента уже в `client_feed`).
- **Показывает:** карточки: модель · цена · % ниже рынка* · 🟢🟡🔴 светофор · балл/10 · свежесть. Пагинация/инфинит.
- **Действия:** тап → карточка; быстрый фильтр по категории.

### 4.3 Карточка находки
- **ЦКП:** готовое к действию решение, не просто ссылка.
- **RPC:** `find_get(p_lot_id)` (контракт «склад находок» §4 спеки) → при покупке `find_buy(p_lot_id, buy_price?)`.
- **Показывает:** модель · цена/выгода* · навар* · состояние (working/dead/unknown) · 🟢🟡🔴 + причины словами ·
  «что спросить продавца» · регион/свежесть · ссылка.
- **Действия:** `[Написать продавцу]` (открыть Avito-url) · `[Купил → в журнал]` (`find_buy`, идемпотентно) ·
  `[Слежу]` · `[Мимо]`. Красный светофор — показываем с ⚠️, не прячем (RR-06).

### 4.4 Журнал · Список сделок
- **ЦКП:** вся бухгалтерия перекупа здесь (замена экселя).
- **RPC:** `journal_list({status?, limit, offset})` (строки `deal_ledger`, RLS-scoped).
- **Показывает:** строки: товар · навар/маржа* или «в наличии» · дней в обороте · статус. Фильтр по статусу.
- **Действия:** тап → сделка (4.5); кнопка «+ Сделка вручную» (`journal_add`).

### 4.5 Сделка · Детали/редактирование
- **ЦКП:** правим любую цифру, отмечаем продажу, видим разбор навара.
- **RPC:** `journal_get(p_id)` *(маленькое серверное дополнение — сейчас детали берём из `journal_list`)* ·
  `journal_update(p_id, payload)` · `journal_mark_sold(p_id, sell_price, sold_at?, channel?)` · `journal_delete(p_id)`.
- **Показывает:** разбор «закупка + расходы (доставка/ремонт/комиссия/дорога/прочее) → навар, маржа %» (RR-10);
  жизненный цикл (в наличии→продано/возврат/ремонт/списано); метка «оценка»/«факт».
- **Действия:** визард «Отметить продажу» (цена→дата→канал); правка полей; мягкое удаление (`status='archived'`).

### 4.6 Дашборд · Статистика
- **ЦКП:** деньги одним экраном.
- **RPC:** `journal_dashboard()`.
- **Показывает:** прибыль за период · число сделок · % в плюс · средняя маржа · деньги в товаре (оборотка) ·
  оборачиваемость (дней) · топ/анти-категории · кэшфлоу. Кнопка «Выгрузить» (Sheets, §7).

### 4.7 Настройки · Конфиг клиента
- **ЦКП:** сам крутит фильтры.
- **RPC:** `config_get()` · `config_update(payload)` (валидация диапазонов, RR-09).
- **Показывает/правит:** категории · N% по категориям · регионы/города · стоп-/include-слова · min_score ·
  свежесть · тихие часы · активность.

### 4.8 Онбординг · Инвайт-код
- **ЦКП:** чужой не зайдёт; свой активируется кодом.
- **RPC:** `redeem_invite(p_code)` (§3.2, к написанию).
- **Показывает:** поле кода → успех → переход на Дайджест; ошибка → «код неверный/использован».

## 5. Навигация
Нижний таб-бар (нативно для mini-app): **Главная · Находки · Журнал · Настройки**. `BackButton` Telegram — назад
из карточек/сделок. Карточка/сделка — модалки или под-экраны. Дашборд — вкладка внутри «Журнал» или блок Главной.

## 6. Тема — авто под Telegram
CSS-переменные из `Telegram.WebApp.themeParams` (`bg_color`, `text_color`, `hint_color`, `button_color`,
`secondary_bg_color`…); реакция на `colorScheme` (light/dark) и событие `themeChanged`. Нативные `MainButton`
(основное действие экрана: «Купил», «Отметить продажу», «Сохранить») и `BackButton`. `HapticFeedback` на тапах.

## 7. Роль бота и Sheets-мост
- **Бот — полноценный, через кнопки/визарды** (решение владельца). `tg_router`/`tg_poll` уже есть (`/журнал`,
  `/купил`, `/продал`, callbacks buy/track/skip). Апгрейд на фронт-этапе: голые id-команды → инлайн-кнопки и
  пошаговые диалоги (визарды) + кнопка **«Открыть приложение»** (web_app-кнопка → mini-app). Зовёт те же RPC.
- **Активация журнал-бота:** вписать bot-token в n8n-credential (сейчас заглушка `PASTE_YOUR_BOT_TOKEN`) и
  `active:true` в `journal_bot_workflow.json`.
- **Sheets-мост** (после ядра mini-app): коннектор читает `journal_list`/`config_get` → лист; правки листа →
  `journal_update`/`config_update` (backend-design §8). Привычка перекупа к таблице остаётся.

## 8. Хостинг (mini-app нужен публичный HTTPS)
| Вариант | Плюс | Минус | Вердикт |
|---|---|---|---|
| **GitHub Pages** | бесплатно, HTTPS, git-native (push→деплой), всё в `resutomaru/-` | публичность репо/Pages | **рекоменд. для прототипа** |
| Vercel/Netlify | free, авто-деплой из git, домены, serverless | +вендор, чуть настройки | апгрейд-путь |
| Supabase Storage | один вендор с БД | менее удобно для SPA | запасной |
**План:** mini-app в папке `app/` репозитория → GitHub Pages (`https://resutomaru.github.io/-/app/`). Anon-key и
project-URL в клиентском конфиге (anon публичен — безопасно). Апгрейд на Vercel при своём домене.

## 9. Предохранители фронта (карта на risk-register)
- **RR-07 (спам/потоп):** лимиты/тихие часы/дедуп — уже на сервере (`push_queue`). Фронт их не обходит.
- **RR-08 (чужие данные):** изоляция на сервере (RLS + `verify_initData`) — проверена (ghost=0). Фронт не фильтрует сам.
- **RR-09 (кривой конфиг):** валидация в `config_update`; фронт показывает `error.msg`, не падает.
- **RR-04 (фейк-выгода):** цена/навар «в тесте» до рубильника — фронт прячет ценовые строки или метит «тест».
- **Fail-safe:** RPC-ошибка → понятное сообщение + повтор; Telegram/сеть легла → оффлайн-заглушка, не белый экран.
- **RR-14 (секреты):** в клиенте только anon-key; bot-token/service-key/ProxyAPI — на сервере.

## 10. Порядок сборки (пилон за пилоном; бэкенд не трогаем)
1. **Каркас:** `app/` (shell + Telegram SDK + авто-тема + `rpc()`-хелпер) + онбординг (`redeem_invite`).
   Деплой на GH Pages, регистрация Web App в BotFather. Смоук: `me()` → vovchik.
2. **Находки:** лента (`finds_list`) + карточка (`find_get`) + `find_buy`. Цена «в тесте» до рубильника.
3. **Журнал:** список (`journal_list`) + сделка (`journal_update`/`mark_sold`/`add`/`delete`) + дашборд.
4. **Главная/Дайджест:** композиция находок + сводки (стартовый экран).
5. **Настройки:** `config_get`/`config_update`.
6. **Бот-апгрейд:** инлайн-кнопки/визарды в `tg_router` + «Открыть приложение» + активация журнал-бота (token, active).
7. **Sheets-мост.**
Каждый пилон: код → смоук на себе (shadow) → проверка → дальше. «Тихо лучше, чем ложно» в силе.

## 11. Что нужно от владельца (разблокирует пилон 1)
1. **`bot_token` в Supabase Vault** — без него `verify_initData` падает `CONFIG: bot_token missing` (гейт ВСЕГО auth).
2. **BotFather:** создать/настроить Web App у бота (URL mini-app), menu-button «Открыть приложение».
3. **Supabase project URL + anon-key** (anon публичен — можно встраивать в клиент).
4. **GitHub Pages** включить для репо (или выбрать Vercel).
5. **Сверить telegram user_id Вовчика** в `client_identities.external_id` (§3.4) — иначе вход не сматчится.

## 12. Открытые решения (влияют на детали, не на каркас)

2. Список расходов/статусов сделки под практику Вовчика (подтвердить поля 4.5).
3. Тексты «что спросить продавца» по категориям (контент, не код).
4. Нужен ли импорт старого экселя в журнал на старте или позже (Ф2).
