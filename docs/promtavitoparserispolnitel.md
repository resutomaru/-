## Что строим (коротко)

Telegram-бот, который мониторит Авито на свежие выгодные лоты по компьютерным комплектующим, оценивает каждый лот по 10-балльной шкале и шлёт уведомления только по самым сочным. **Мульти-тенант:** один общий сбор данных, индивидуальные фильтры на каждого клиента. Этап 1 — рабочий прототип под одного пользователя (Вовчик, перекуп б/у комплектухи). Этап 2 — продукт для других перекупов с настройкой под себя.

---

## Архитектура (зафиксирована)

```
rest-app API (Авито, один сбор на всех)
        ↓  поллинг каждые 2 мин, дельта по новым ID
n8n: сбор + дедуп (глобальный seen-ID)
        ↓
Postgres (Supabase): лоты · история цен · медианы · seen-ID · лог отправок · зеркало конфигов
        ↑  раб/нераб тег (на лот) + медиана по позиции (почасово)
        ↓
Фильтр + скоринг на клиента (гейты → балл 0–10), конфиг читается из Google Sheets
        ↓  дедуп отправок на клиента
Telegram (1 бот, чат на каждого клиента)
```

Два хранилища: **Postgres** — тяжёлые данные движка; **Google Sheets** — лёгкий конфиг на клиента (редактирует человек). Дирижирует всем n8n.

## Зафиксированные решения

**Источник данных.** rest-app API. Анти-бот Авито — на их стороне, свой скрейпер НЕ пишем. Разовый batch-сид для заполнения истории цен, дальше инкрементальный поллинг каждые 2 минуты только по новым ID.

**Бенчмарк цены — медиана б/у по позиции, из СВОИХ данных.** Никаких DNS/Я.Маркета. Каскад:
- основная медиана — по `(модель + производитель)`, если в бакете ≥ **K = 8** лотов за окно;
- иначе откат на медиану по `(модель)`;
- лоты без распознанного бренда судятся на уровне модели.
- Окно — **30 дней**, по всей России, **только рабочие** экземпляры, с отсечкой выбросов (защита от опечаток и дохлых, утягивающих медиану).
- Медиана пересчитывается **почасово** (за 2 минуты цена не двигается — незачем чаще). Новый лот сверяется с кэшированной медианой.

**Жёсткие гейты (лот обязан пройти ВСЕ, иначе не уведомляем):**
1. Свежесть — лот впервые увиден в текущем цикле (по сути обеспечивается 2-мин дедупом).
2. Рабочее — `мёртвое` выкидываем совсем; `неясно` проходит, но получает штраф в балле.
3. Цена ≤ `медиана × (1 − N%/100)`.

**N% по категориям (настраивается на клиента):**
- видеокарты, процессоры, память, материнки → **40%**;
- SSD/NVMe и блоки питания → **55%** (только аномально выгодные; эти категории берём ТОЛЬКО при таком прайсе).

**Скоринг 0–10** среди прошедших гейты — ранжирует выживших, чтобы сочные были вверху. Веса (по правкам клиента):
- высокий: дата публикации (свежее = выше), отклонение цены от медианы (глубже скидка = выше), ясность «рабочее» (рабочее > неясно);
- средний: слова срочности («срочно», «переезд», «продаю быстро»), состояние (новый/коробка);
- низкий: рейтинг продавца, кол-во отзывов, срок на Авито;
- НЕ используем: «описание не пустое» (Авито не даёт публиковать без описания), локацию/доставку (вторично).

**Категории.** Берём: видеокарты, процессоры, память, материнки (полный мониторинг); SSD/NVMe, блоки питания (только аномальный прайс). НЕ берём: HDD, корпуса, кулеры, периферию. **Целые сборки и ноутбуки** — это не комплектующие, и они загрязняют поиск по компонентам («RTX 3070» внутри готового ПК) → нужен классификатор `отдельный компонент / сборка / на запчасти`, сборки отсекаем.

**Классификатор раб/нераб — гибрид (контроль стоимости LLM).**
- Сначала дешёвый regex-проход.
  - мёртвое: «на запчасти», «на запасные части», «не включается», «не работает», «не запускается», «нет изображения», «артефачит».
  - рабочее: «на гарантии», «гарантия до», «чек есть/сохранён», «полностью рабочая», «идеально работает».
  - флаг износа (не мёртвое, но штраф в балле): «после майнинга».
  - «не тестировал / не проверял» → `неясно`.
- LLM (дешёвая модель) — ТОЛЬКО на спорную середину, которую regex не разрулил.
- Выход: `рабочее / мёртвое / неясно`. `мёртвое` — hard-drop И исключается из расчёта медианы.

**Хранилище — Supabase Postgres (бесплатный тариф).** Таблицы (минимум): сырые лоты; история цен; медианы по позиции; `seen_ids` (с TTL/чисткой — иначе растёт бесконечно); лог «отправлено клиенту X»; зеркало клиентских конфигов из Sheets.

**Конфиг на клиента — Google Sheets.** Поля: категории, N% по категориям, ключи-include, стоп-слова, регион/город, окно свежести, `chat_id`. n8n читает лист по расписанию и синкает в Postgres. (Для прототипа — один лист со строкой на клиента; для массового продукта — лист на клиента или UI, это фаза 2.)

**Дедуп двухслойный:** глобальный `seen_id` (ингест, «лот вообще новый?») + лог отправок на клиента («этому клиенту уже слали?»). Иначе пересекающиеся фильтры и любая правка конфига → спам старыми лотами.

**Доставка.** Один Telegram-бот, `chat_id` на клиента из конфига. В уведомлении: модель + производитель, цена, % ниже медианы, балл 0–10, ссылка, краткий флаг состояния.

## Порядок сборки

**Фаза 0 — проверка rest-app (ДО всего остального).**
На тестовом 15-дневном доступе и через их поддержку выяснить:
- (а) поддерживается ли выборка ТОЛЬКО новых лотов — сортировка/фильтр по дате, курсор по времени;
- (б) модель тарификации — за запись / подписка / за запрос.

Если дельта-выборка НЕ поддерживается ИЛИ тарифицируют за весь стоячий список при каждом запросе → **СТОП, сигнал Алексею:** 2-минутный поллинг «всего» нежизнеспособен на этом источнике. Альтернатива — парсер, заточенный под автоматический сбор по расписанию (в обзорах парсеров Авито такие есть). Не строить дальше, пока ингест не подтверждён.

**Фаза 1.** Схема Postgres (SQL по таблицам выше).

**Фаза 2.** Ингест: n8n-воркфлоу, поллинг каждые 2 мин, дельта-выборка, дедуп по `seen_id`, запись сырых лотов. Плюс разовый batch-сид для истории.

**Фаза 3.** Нормализатор позиции (по категориям): извлечение канонической `(модель + производитель)` из заголовка. **Это сердце точности** — кривой нормализатор = кривая медиана = ложные «ниже рынка». Делать тщательно, тестировать на реальных заголовках. У каждой категории свой ключ позиции (видеокарта: модель+чип+бренд; SSD: бренд+объём+интерфейс; БП: бренд+мощность+сертификат).

**Фаза 4.** Классификатор раб/нераб (regex + LLM-гибрид) + детектор сборок/запчастей.

**Фаза 5.** Почасовой job: медиана по позиции (каскад, working-only, отсечка выбросов).

**Фаза 6.** Фильтр + скоринг на клиента (гейты → балл), чтение конфига из Sheets.

**Фаза 7.** Telegram-доставка + дедуп отправок на клиента.

**Фаза 8.** Конфиг-слой Sheets (схема листа, синк в Postgres), проверка на втором тестовом клиенте — убедиться, что фильтры реально разъезжаются по клиентам.

---

## Тестирование

На каждом узле — реальные данные, Алексей запускает и репортит. Особое внимание на три источника ложных результатов:
1. нормализатор кладёт разные варианты в один бакет (3070 и 3070 Ti вместе) → кривая медиана;
2. классификатор ставит «рабочее» мёртвому;
3. перепутанный вариант модели → ложное «ниже рынка».

---

## Чего НЕ делать

- НЕ писать свой скрейпер Авито (анти-бот на стороне rest-app).
- НЕ звать DNS/Я.Маркет — бенчмарк только из своих данных.
- НЕ класть тяжёлые данные в Google Sheets (только конфиг).
- НЕ делать отдельный сбор с Авито на каждого клиента (один общий сбор, фильтры поверх).

---

## Известные риски (держать в голове)

- Глубокая скидка (−40% и ниже) коррелирует с разводом/скрытым дефектом → гейт «рабочее» и сигналы продавца критичны на экстремумах.
- Единый rest-app аккаунт — единая точка отказа: бан кладёт всех клиентов разом. Мониторить.
- Стоимость LLM держать гибридом (regex отсекает очевидное).
